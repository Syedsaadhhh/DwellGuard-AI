### Verdict

**Proceed. Do not restart ideation.**

DwellGuard is competitive if the build proves this exact sentence:

> A driver's spoken limits visibly change the dock call, and the resulting appointment visibly returns to the driver.

That is the project. The generic pattern is not unique; the precise product experience can still be memorable. Do not say “first,” “only,” “never seen,” or “fully autonomous.” Say exactly what the recorded run proves.

### Winner discipline to borrow

[FirstFrame](https://devpost.com/software/firstframe) won by making one improvement visible almost immediately, measuring it inside the product, making sponsor technology load-bearing, exposing failure behavior, and letting judges inspect a real deployed path.

Apply that discipline here:

- **One sentence:** The delay happened. The plan kept moving.
- **One visible transformation:** broad authority → driver-approved overlap → confirmed dock time.
- **One measured outcome:** authorization-to-confirmation duration from persisted event timestamps.
- **One undeniable sponsor role:** actual CALL-E call IDs and recipient evidence determine the next action.
- **One honest failure:** a fee or conditional offer outside authority becomes “Dispatcher needed,” never green.
- **One frictionless judge path:** a clearly labelled public replay works without credentials and cannot dial.

Do not imitate FirstFrame's design. Reuse its proof discipline.

## 2. Locked product

### Product sentence

DwellGuard calls the driver and receiving dock to arrange a late truck's revised appointment within dispatcher-approved limits, then returns the confirmed plan to the driver.

### Controlled demo participants

- One dispatcher operating the desktop application.
- One consenting driver role-player.
- One consenting receiving-dock role-player.
- Two CALL-E phone tasks.
- One browser acknowledgment on the driver's already-open handoff page.

The browser tap is not a third phone call. The driver acknowledgment is receipt of the plan, not proof of identity, physical arrival or unloading.

### Authority once

Before anything starts, the dispatcher approves:

- exact driver and dock contacts;
- shipment/load reference;
- earliest and latest acceptable local time with IANA timezone;
- fee ceiling and currency;
- two-call task budget;
- whether DwellGuard may choose a dock time inside the driver's explicitly approved interval;
- expiration time;
- stop control and human-handoff rules.

Freeze this as an immutable authority version. Any meaningful change creates a new version and blocks stale work.

### Three truthful outcomes

1. **Plan confirmed**: recipient-attributed evidence supports the exact appointment and frozen authority.
2. **Driver received**: the current receipt version was acknowledged through its scoped handoff token.
3. **Dispatcher needed**: the result is incomplete, conditional, conflicting, outside authority, stopped or uncertain.

Never merge these into one green “success.”

## 3. The signature wow moment

Name the component **Plan Rail** in code and product copy.

### Before the driver result

Show on one shared time axis:

- original appointment;
- operator-approved interval;
- updated ETA;
- “Waiting for driver's workable window.”

Do not show warehouse availability before the dock supplies it.

### When the driver result is verified

The same Plan Rail changes in place:

1. the driver-approved interval appears;
2. the valid overlap is highlighted;
3. impossible time fades but remains visible;
4. a compact “What changed” sentence appears;
5. the dock request preview updates from real server state.

Example:

> Driver can check in 11:35 to 11:50 and authorized selection inside that range. Asking Northline Receiving for one explicit time within 11:35 to 11:50.

This transformation must be caused by persisted timestamps and verified recipient evidence. No scenario-name branch, hardcoded answer or client-only timer may choose it.

### When the dock confirms

The Plan Rail resolves to the exact confirmed point/window. Beside it, display a paper-like appointment pass:

- **11:45 AM**
- full date and timezone;
- Northline Receiving;
- Door 6, only if established;
- fee and currency, including “No additional fee” only when supported;
- confirmation basis;
- receipt ID/version;
- “Sending plan to driver.”

The driver's already-open phone page updates to the same receipt. When the driver taps **I've received this plan**, the desktop changes to **Driver received** with the acknowledgment timestamp.

This two-device relay is the final demo image. Keep both screens visible long enough to be understood.

### Ten-second cold-viewer test

A person seeing only the main screen for ten seconds must be able to answer:

1. What went wrong?
2. What changed?
3. What is happening now?
4. What, if anything, needs a person?

If the screen fails this test, remove information before adding explanation.

## 5. Technical contract

### Stack

Next.js App Router, strict TypeScript, Tailwind, Zod, official @call-e/calle SDK, Supabase Postgres, Vitest and Vercel.

Use one package manager and lockfile. Choose stable versions once. Do not upgrade during polish without a concrete blocker.

No extra LLM, SMS provider, maps, billing, telematics, TMS, EDI or warehouse-booking API. The problem does not need them.

### Boundaries

Business logic depends on:

- Store interface;
- CalleGateway interface;
- system clock;
- token generator.

Provide a deterministic MemoryStore for isolated fixtures and a real SupabaseStore for deployed state.

The browser never owns workflow execution. Refreshing or closing it must not cancel server-owned progress.

### Minimal persisted records

- incidents
- authority_versions
- call_intents
- call_snapshots
- observations
- workflow_jobs
- receipts
- handoff_tokens
- handoff_acknowledgments
- audit_events

Every business transition carries incident ID, authority version and state revision.

### CALL-E provider contract

Verify the installed SDK in Run 1. Save the top-level CALL-E CallTask ID as calle_call_id. Keep attempt-level provider_call_id separate if present.

Before external I/O:

1. validate frozen authority;
2. reserve the two-task budget atomically;
3. create the semantic call intent;
4. persist the exact request and stable idempotency key;
5. claim the job with a fenced lease;
6. send the request.

After creation, persist the returned CallTask ID immediately.

Recovery rules:

| State | Action |
| --- | --- |
| Request not sent | Resume the same intent. |
| Response lost but exact request/key saved | Replay only that exact request/key using documented recovery behavior. |
| CallTask ID known | Retrieve the existing task only. |
| ID and reproducible request both unavailable | CREATE_UNCERTAIN; no automatic redial. |
| Duplicate webhook | Acknowledge or resume the same job; no duplicate effects. |
| Dock confirmed but receipt write failed | Finalize from persisted evidence; never call again. |
| Stop/revision changes while call active | Block later dispatch and reconcile the possible external result. |

Incoming webhook content is a hint, not trusted business evidence. Persist the event first, retrieve the authoritative stored CALL-E task with server credentials, validate it, then advance. Do not return success while depending on an unawaited promise.

Provide a bounded recovery worker command. If hosted scheduling is not verified, run the worker during the demo and disclose that dependency.

### Evidence boundary

Provider completion, schema validity or confidence does not prove an agreement.

Critical facts require recipient-attributed support:

- correct shipment/load;
- full date;
- local time and IANA timezone;
- appointment meaning;
- dock/door if claimed;
- fee amount and currency;
- conditions;
- driver selection permission.

Preserve corrections and qualifiers. A bot question is not recipient evidence. Empty, unknown, conditional, contradictory or clipped values cannot commit.

### Time and authority rules

- Preserve full dates and timezone offsets.
- Handle midnight and date rollover.
- Never fall back silently to 09:00 or another invented time.
- Compute intersection only from operator authority and verified driver limits.
- Before dock confirmation call the intersection **within our limits**, not warehouse availability.
- A dock point/window outside the intersection cannot commit.
- Unknown fee, wrong currency, conditional offer or amount above authority becomes Dispatcher needed.
- Two CALL-E tasks maximum for the golden run.
- Stop prevents future tasks; it cannot promise cancellation of a call already created.

### Access and privacy

Live writes and private reads require a short-lived server-verified operator session. Use a signed HttpOnly, Secure-in-production, SameSite cookie and request-origin/CSRF protection. Rate-limit login, writes and webhooks.

Handoff tokens:

- minimum 192 bits of randomness;
- stored hashed;
- scoped to one incident and receipt version;
- short expiry;
- no third-party assets or analytics;
- no private transcript;
- no operator controls;
- idempotent acknowledgment;
- no-store and no-referrer responses;
- possession grants acknowledgment only, not booking authority or identity proof.

Public /demo uses separate fixture state and can never reach live routes.

### Locked specialty: Spoken Constraint Relay

> The driver's spoken boundary visibly rewrites the dock call before it is placed; the dock's commitment returns as the same versioned plan on the driver's phone.

### Irreplaceable product artifact: Causal Appointment Proof

Add one compact, real artifact that competitors cannot reproduce with a nicer dashboard alone. Every confirmed plan must carry a **Causal Appointment Proof**: a deterministic, privacy-safe proof of why this exact appointment was allowed.

The proof chain is:

**Frozen authority version → attributed driver interval and selection permission → derived overlap → attributed dock commitment → current receipt version → driver acknowledgment**

Implementation requirements:

- Build a canonical JSON payload from incident ID, authority version, both top-level CALL-E CallTask IDs, normalized driver interval and permission, derived overlap, exact dock time/door/fee/currency/conditions, receipt version and acknowledgment timestamp when present.
- Exclude phone numbers, names, raw transcripts, API keys and provider response dumps.
- Compute SHA-256 on the server and persist the complete payload plus a short display ID such as `DG-PROOF-7A91C2E4`. Do not call it blockchain.
- Finalize a proof only when every required causal link is valid. Missing, conflicting, expired or conditional evidence leaves an amber broken link and ends as **Dispatcher needed**; it must never produce a green proof.
- The same proof ID and receipt version must appear on the desktop appointment pass and driver handoff page. The acknowledgment appends a final auditable event without changing the already-confirmed appointment facts.
- Show the chain directly below the Plan Rail as one quiet band titled **Why this plan is valid**. Each link shows one fact and source, not internal jargon. Keep detailed evidence expandable.
- Add focused tests: canonical ordering is stable; changing any appointment fact changes the hash; missing evidence cannot finalize; the payload contains no phone number/name/transcript; restart/Supabase retrieval returns the same proof.
- In the demo, hold desktop and phone together on the matching proof ID, then tap acknowledgment and show the last link change to **Driver received**.

This is not an extra analytics feature. It is DwellGuard's inspectable trust artifact and the technical reason the visual relay is credible.

### Mandatory Run 1 repair gate (verified against `98de93e`)

Run 1's typecheck, unit tests and production build are valid, but they only prove the synchronous fixture path. Before any real call, fix these inspected defects inside Run 2:

1. **Repair asynchronous CALL-E reconciliation.** `advanceIncident` creates a call only while status is `authorized`. If CALL-E returns `in_progress`, the incident becomes `driver_task_pending`; later worker/webhook calls never retrieve and apply the completed result, so the live workflow stalls. Add one persisted reconciler for known `calle_call_id` values that retrieves the existing task, stores a deduplicated snapshot/observation, and resumes the state machine. Use it from both the webhook and recovery worker. Add a queued → completed test for both driver and dock; prove exactly two creates and retrieval-only recovery.
2. **Fail closed outside the public replay and use the official endpoint.** `getCalleGateway()` currently falls back to `FixtureCalleGateway` when `CALLE_API_KEY` is absent, so operator endpoints can report simulated progress instead of `BLOCKED_LIVE`. Permit the fixture gateway only through `getDemoContext()`; live routes must return a clear non-2xx `BLOCKED_LIVE` response without credentials. The official SDK defaults to `https://api.heycall-e.com`; DwellGuard currently overrides that with the incorrect fallback `https://api.call-e.com`. Remove the override and let the SDK use its official default, or validate `CALLE_BASE_URL=https://api.heycall-e.com`. Add a no-network configuration test.
3. **Enforce the access and current webhook boundary.** The signed-session helpers exist but are unused. Protect all private incident reads and every create/authorize/advance/stop action with a server-verified short-lived operator session plus origin/CSRF checks. Remove the production fallback secret. Current CALL-E terminal webhooks are unsigned: require `CALL-E-Event-Id`, require it to equal the body event `id`, persist/deduplicate that event ID, map the CallTask ID to a saved intent, then re-fetch authoritative state with server credentials. Never choose an incident solely from webhook metadata and do not implement the deprecated SDK 0.2 signature contract.
4. **Make durable mode match its claims.** The migration currently implements atomic budget reservation only; `claimJob` is not a fenced lease and the recovery worker does not claim jobs. Implement atomic authority versioning, revision-guarded transitions and a real lease/claim procedure, then exercise the Supabase path with a focused integration test. Do not silently use process memory for a deployed live run.
5. **Fix production handoff persistence.** The domain always creates `raw_token_display`, but the Supabase `handoff_tokens` table has no such column; inserting the full object can fail. Persist only the token hash and metadata, return the raw token once for delivery, and never expose hashes or raw tokens through private incident JSON. Enforce authority expiry before dispatch and make latest-version receipt/token queries deterministic.
6. **Add repository proof.** `98de93e` has no reported GitHub status checks. Add one minimal CI workflow for typecheck, tests and production build, then require a green run before release.

Do not spend live-call credits until items 1 to 5 pass. These repairs are part of Run 2, not a new run.
